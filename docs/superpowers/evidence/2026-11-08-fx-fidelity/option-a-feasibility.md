# Option A: compilation-route feasibility

Date: 2026-11-08. Read-only source audit; no source changes, builds, tests, server changes or Git mutations performed. This report does not establish runtime acceptance.

## Verdict

**STOP at the owner's four-route feasibility gate.** Extending the existing per-app Vite resolution can supply Option A bindings to source applications compiled with that plugin, including app fixtures and packed consumers. It cannot supply missing lexical bindings to arbitrary, already-compiled unbound modules admitted through the current `BundleLoader`/explicit-composition contract. That route does not require the plugin, carry compilation/binding metadata, or expose an import-resolution step.

This is a missing compilation contract for route 4, not a claim that per-app bound subclasses are generally infeasible. Existing inline test classes outside an `.app` folder are also not automatically bound, but rejecting attributed construction from their base imports is intentional under Option A; they are not a separate fundamental blocker.

## Resolver, generated exports and identity

- Discovery resolves `Contents/Info.ts` and `Contents/index.tsx`, derives and validates the manifest, and records `bundleIdentifier` with `entryPath` (`scripts/synware/vite-plugin.mjs:424–450`). It rejects duplicate bundle identifiers in that discovery.
- The current `resolveId` only binds the exact root import `@syndromatic/syncloudos`. It requires a non-virtual importer, strips the query suffix, checks containment in the discovered `.app` directory, and returns `\0virtual:syncloudos/app/<normalised-id>` (`729–735`). It does not currently bind any `/fx/<family>` import.
- `load` generates that module once per resolved module identity (`740–741`). `src/SynCloudOS/AppSDK/scos/appModuleSource.mjs:2–3` re-exports the base root, imports the existing SDK implementation, and exports one module-level `SCOS = createAppSCOS(appId)`. The virtual importer's exclusion in `resolveId` prevents the re-export from resolving recursively to itself. A per-app/per-family virtual identity is an ordinary extension of this mechanism; no FX subclass generator exists in the audited baseline.
- Attribution is based on the **file containing the import**, not the caller of a shared helper. A callback declared in app code retains its imported binding through `await`, timers or third-party invocation. A helper in a separate shared/node_modules file is not attributed merely because an app calls it. This matches the requested rejection of base attributed construction outside `.app`; pure exports can continue through the base family export.
- Packed SDK entries are built together (`scripts/synware/build-sdk.mjs:145–191`) and include explicit FX-family entry points (`scripts/synware/sdk-entries.mjs:21–49`). This supplies the existing shared-module path. It does not establish cross-build deduplication of a separate, self-contained precompiled application with its own SDK copy.

## Existing SCOS session lookup

`createAppSCOS` stores an app ID and resolves it when used (`src/SynCloudOS/AppSDK/scos/scosFacade.ts:244–248`). The existing registry is keyed by normalised app ID, removes disposed registrations, filters aborted contexts, rejects no live session and rejects multiple distinct runtime IDs (`scosSessionRegistry.ts:34–63`). Context creation registers the session and unregisters it on abort (`src/SynCloudOS/AppSDK/createSynWareContextValue.ts:427–430`).

This provides the requested SCOS-style live lookup independently of a synchronous call stack. It also means an app ID is not a selector for two simultaneously live runtimes of the same app: current SCOS intentionally reports ambiguity. Binding a class during module evaluation need not resolve a live session; constructing an attributed object before a live session exists must remain distinguishable from merely importing that class. No hostile same-realm security claim follows from these mechanics.

## Test-host evaluation boundary

`CreateSynWareTestHostOptions` currently has only the `app` definition and `application` class alternatives (`testHostTypes.ts:247–250`). `createSynWareTestHost` immediately converts the supplied class or consumes the supplied definition (`149–156`). Its apparently lazy `loadModule` only waits on a gate and returns the already-captured `appDefinition` (`171–176`); it does not import an entry module.

The 6e consumer imports `SearchApplication` before calling the host (`consumer.test.tsx:3–12`). Its source is a discoverable `.app` with direct FX imports (`src/SynWare/Search.app/Contents/index.tsx:1–4`), but its Vitest config has no project plugin (`vitest.config.ts:1–2`). The root framework Vitest configuration instead aliases public SDK entries straight to source (`framework/vitest.config.ts:21–34`). Those are concrete wiring gaps. Compiling a `.app` fixture with the plugin gives it identity before evaluation; the existing host can then consume a previously bound class, while the requested per-app-entry API remains to be implemented. No retroactive binding of every legacy inline test class is required by this finding.

## Installed/precompiled boundary: exact stop condition

The plugin's project module contains a statically emitted `loadModule: () => import(<absolute app entry>)` (`vite-plugin.mjs:310–322`). That import is visible to the source build, so its emitted dynamic chunk can already contain the binding. Installed PWAs produced by this plugin reuse the build's emitted assets: `scripts/synware/pwa-plugin.mjs:29–38,59–81` generates manifests, asset lists and the worker, not a second app-import compiler.

The general installed-bundle contract is wider. `SynCloudOSBundleModuleLoader` is simply `() => Promise<SynCloudOSAppModule>` (`bundleTypes.ts:65`), and a browser descriptor's loader is checked only for being a function and forwarded unchanged (`browserRuntime.tsx:277–313`). `BundleLoader` calls it without arguments, or returns an eager definition; only after the promise resolves does it capture/validate the module (`BundleLoader.ts:332–359`). `definitionModule.ts:68–104` validates the default export and manifest, not the module's import graph. Explicit compositions without the plugin are expressly supported (`projectComposition.ts:39–56`; `getting-started.md:142–146`).

**Missing contract:** nothing currently requires those externally supplied/precompiled application modules to have passed through the app-aware compiler, establishes which FX binding they contain, or ensures they share the host's SDK/session-registry graph. A registered manifest/app ID cannot rewrite lexical references in a previously compiled/evaluated module. The audit therefore cannot confirm route 4 as universally bindable under the requested extension. No workaround or replacement architecture is proposed here.

## HMR and cache paths

- Ordinary app class source updates may remain local: `scripts/synware/hot-applications.mjs:225–242` records hot modules and appends registration/acceptance code (`205–216`); the project plugin returns early for accepted updates (`vite-plugin.mjs:776–778`). The per-app virtual ID does not contain the importing file or a timestamp, so unchanged virtual modules can be shared by all files of the same app in that module graph.
- Discovery/manifest/resource changes refresh discovery and trigger a full reload (`vite-plugin.mjs:650–668,682–688,779–787`). Explicit invalidation currently names the project and typography modules, not the per-app SCOS virtual modules (`663–668`). The full reload is material to identity changes; this audit does not assume that targeted FX-module invalidation already exists.
- The packed SDK dependency-cache key hashes the packed package manifest, top-level `.js` entries and chunk filenames (`vite-plugin.mjs:604–614`) and adds that fingerprint to `optimizeDeps` (`701–706`). It does not hash `.mjs` plugin/generator files, and `pluginSdkBuild` is cached per plugin module. Existing test source covers changed SDK entries/chunks and the absent source-checkout fingerprint (`tests/runtime/synware-vite-sdk-build.test.ts:21–34`), not an FX generator-only update. These are verification requirements for a future compiler change, not proof of a new binding implementation.

## Disposition

Routes 1 and 3 have the required compilation identity. Route 2 can obtain it through the requested compiled `.app` fixture and entry wiring. Route 4 only has it when its code was already compiled with the binding and reaches the shared SDK registry; the current arbitrary-loader/no-plugin contract does not guarantee either. Implementation remains stopped under the owner's gate.
